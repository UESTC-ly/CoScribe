# 贡献指南

> 本页与根 `AGENTS.md`、当前 Git 历史和测试脚本于 2026-07-31 对齐；若约定冲突，以根 `AGENTS.md` 和可执行检查为准。

## 开始前

1. 从 `main` 或已有功能分支创建清晰的工作分支。
2. 阅读 [开发指南](./development.md)、[系统架构](./architecture.md) 和 [安全与 AI Shell](./security-and-ai-shell.md)。
3. 先搜索已有组件、类型、IPC 和测试模式，避免平行实现。
4. 仅修改与任务直接相关的文件；不要重置或覆盖工作区中其他人的改动。

## 变更要求

- 保持 TypeScript 严格类型、现有 ESM 风格和两空格缩进。
- 不新增依赖，除非明确批准且现有工具无法解决需求。
- 用户可见功能提供完整状态：加载、空态、错误、禁用、键盘和窄窗口。
- 需要主进程能力时按共享类型 → IPC 通道 → main handler → preload → UI 的顺序实现。
- 文件、密钥、网络、浏览器、MCP 和终端改动需要最小权限、用户确认和主进程测试。
- 任何 AI 写文件能力必须保留预览、接受、冲突检测、主进程重验和撤销路径。

## 测试要求

```bash
npm run typecheck
npm test
```

以下场景再增加 E2E：

- 交互流程、布局、键盘快捷键；
- IPC、持久化、文件操作；
- 新窗口、浏览器、终端或系统对话框；
- 打包、原生模块、资源和平台行为。

不要把“测试已收集”或历史报告作为通过证据。报告时写清实际运行的命令、平台、通过数量、跳过项和未覆盖风险。

纯文档变更也要检查相对链接、图片存在性、Mermaid fence 配对和 `git diff --check`。刷新截图应运行仓库脚本并确认 7 张图片都来自临时项目，不能手工替换成无法复现的营销图。

## 提交与 PR

提交信息使用意图优先的主题，并使用 Git trailers 记录关键决策：

```text
<为什么要改>

<约束和取舍>

Constraint: ...
Rejected: ...
Confidence: high
Scope-risk: narrow|moderate|broad
Tested: ...
Not-tested: ...
```

PR 应说明：

- 用户或开发者获得了什么能力；
- 影响的模块和安全边界；
- 验证命令与结果；
- 已知限制；
- UI 改动的截图；
- IPC、文件系统、凭据、终端、MCP 或打包影响。

## 不应提交的内容

- API Key、Token、Cookie、用户资料、真实聊天或用户项目路径；
- `release/`、`out/`、Playwright 结果、覆盖率和其他生成制品；
- 根目录 `/learn/` 的私有交接/学习资料；
- 本地 `CLAUDE.md` 或开发环境专用配置，除非仓库维护者明确要求。
