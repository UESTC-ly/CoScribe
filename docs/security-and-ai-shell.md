# 安全与 AI Shell

## 安全模型

CoScribe 假设以下输入都不可信：Renderer 输入、项目文件名和内容、网页、OCR 文本、AI 回复、MCP 回复、终端输出和第三方 Provider 响应。高权限操作只能在主进程中完成，并且需要最小 IPC 面、输入校验和用户可见确认。

## Renderer 与 IPC

- `nodeIntegration` 保持关闭。
- `contextIsolation` 和 sandbox 保持开启。
- Renderer 只通过 `window.coscribe` 调用白名单 API。
- 不暴露泛化 `ipcRenderer`、文件系统、`child_process`、终端对象或密钥。
- IPC handler 验证可信 sender，再验证输入和权限。

新能力不得绕过 `electron/ipc-channels.ts`、`electron/preload/index.ts` 和 `electron/main/ipc.ts` 的契约链。

## 项目文件保护

主进程为当前项目建立路径守卫：

- 读写目标必须在已打开项目根目录内。
- 拒绝路径穿越、项目外目标和不安全的符号链接。
- 在确认前、写入前重新核对路径、文件身份、修改时间、revision 或 hash。
- 采用原子写入，避免半写入文件。
- AI 仅能提议支持类型的创建、追加或替换；不能静默删除文件。

AI 的“已接受操作”有历史记录，只有目标文件没有后续手工变更时才能安全撤销。

## AI 服务与密钥

密钥只由主进程通过 Electron `safeStorage` 保存。远程 API 地址要求 HTTPS；仅回环本地服务可用 HTTP。密钥不会透过 preload 返回给 Renderer。

将项目内容发送给 AI Provider 是用户选择上下文后的网络行为。重要、敏感或受监管资料应在选择“当前项目”前先做最小化与脱敏。

## AI Shell 规则

AI Shell 是高风险、显式授权能力：

1. 默认关闭。
2. 设置开关只显示开启入口，不授权、不启动、不执行。
3. 每次开启必须显示原生风险警告并再次确认。
4. 授权只在内存中保存，绑定当前项目与本次应用会话。
5. 关闭终端、项目、应用或关闭设置开关会撤销授权。
6. 默认每条命令都需确认；会话模式必须由用户显式选择。
7. 一次 AI 请求最多运行一条命令，且同一项目同时只能有一条 AI Shell 命令运行。
8. 命令长度、运行时间和输出大小受限；控制序列、双向控制字符等会从返回给模型的输出中清理。

AI Shell 命令以当前登录用户权限运行，不受项目路径守卫约束。这意味着即使 cwd 是项目目录，命令也可能读取网络、环境变量或项目外文件，并可能修改系统可写位置。不要批准不理解的命令，不要在不受信任的项目中改成会话授权，也不要把它设计为后台自动化。

## 普通终端与外部终端

普通内置终端也在主进程 PTY 中创建，但它属于用户交互会话，不会自动授权 AI。每个会话与创建它的 Renderer 窗口绑定，最多同时八个。外部终端仅接收经过项目路径校验的工作目录。

## 变更检查清单

涉及安全边界的 PR 至少回答：

1. Renderer 是否仍没有 Node、任意 IPC 和文件系统能力？
2. 新路径是否在主进程重新验证并抵御符号链接/穿越？
3. 新写操作是否有用户确认、冲突检测和原子写？
4. 新网络请求是否避免泄露密钥或未经选择的上下文？
5. 新终端/MCP/外部进程是否默认关闭、可撤销且有可审计确认？
6. 是否新增了主进程和失败路径测试？
